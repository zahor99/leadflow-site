In short

Gergely would take the existing Next.js energy management app from mock data to a fully production-backed system: designing the PostgreSQL schema for buildings, portfolios, invoices, compliance, and bids; building a real API layer with auth, row-level authorization, and a hardened request gate; then wiring every frontend screen to live data. The work proceeds incrementally — no big-bang cut-over — with migrations so any developer can bring up the environment from scratch.

Architecture I'd propose

  • PostgreSQL Schema — buildings, portfolios, roles, invoices, bids, compliance
  • Migrations & Seeds — Drizzle/Prisma; any dev spins up from scratch
  • API Layer — parameterized queries, pagination, filtering, error codes
  • Auth & AuthZ — NextAuth/JWT; row-level scope, fail-closed
  • Hardened Gate — Redis rate-limit, Zod validation, structured logging
  • Next.js Frontend — mock routes replaced screen by screen
Assumes: Assumes NextAuth is acceptable for session handling; a custom JWT flow works equally well · Assumes Drizzle or Prisma for migrations — confirm preference early · Assumes EC2 deploy follows confirmed local parity, not a parallel track — tell me where I'm wrong and the design adapts.

Plan

  • Phase 1 – Schema & Auth (Week 1-2) — Live Postgres schema, migrations, seed data, auth wired up
  • Phase 2 – API & AuthZ (Week 3-4) — All mock routes replaced; row-level authorization enforced
  • Phase 3 – Harden & Deploy (Week 5-6) — Redis rate-limit, Zod, logging, EC2 deploy confirmed
